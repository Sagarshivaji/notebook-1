Overview

Citizens encounter civic issues every day — potholes, garbage dumping, broken streetlights, water leaks and damaged footpaths. Reporting them, however, can feel like completing a government form rather than performing a simple civic action.

This project redesigns the civic reporting experience around a single principle: ask the citizen only what they know, and let the system handle the administrative complexity. The result is a reporting flow that takes seconds, a tracking model that separates submission from verification, and a public layer that shows civic progress without exposing the people who reported it.

Key Design Principles

01

Report in Seconds

The primary action should always be obvious.

02

Ask Only What the Citizen Knows

Where they saw it, what happened, what it looks like. The system determines ward, corporation, department and routing.

03

Don't Confuse Submission with Verification

A citizen submitting a report doesn't mean the issue has been verified.

04

Transparency Without Exposing Citizens

Show aggregated progress and verified outcomes — never reporter identity.

Why “Verifying” Matters

A report can be genuine — or it can be duplicate, outdated, incorrectly located, already resolved, or false.

Don't use

Reported → Resolved

Use

Received → Verifying → Assigned → In Progress → Resolved

This makes the system more trustworthy — the UI never implies that every citizen submission is automatically confirmed.

Privacy Decision

Problem

A public feed saying “Pothole reported 100m away” could potentially allow people to infer who reported it in a small neighborhood.

Don't publicly expose

  • ✕ Reporter identity
  • ✕ Exact home / location information
  • ✕ Unverified individual complaints

Instead, show

  • ✓ Aggregated community progress
  • ✓ Verified / processed outcomes
  • ✓ Approximate areas where appropriate
lock

Solution: Don't expose individual citizen reports publicly. Demonstrate civic activity without unnecessarily exposing citizens.

Trade-offs

balance

1 · Speed vs Information

Decision: Make descriptions optional.

Why: Most users shouldn't have to write a detailed complaint when location + category + photo provide enough initial context.

visibility_off

2 · Transparency vs Privacy

Decision: Don't show individual raw reports publicly.

Why: Transparency should expose civic progress, not citizen identity.

fact_check

3 · Accuracy vs Friction

Decision: Verification happens after submission.

Why: Asking citizens to provide excessive proof would make reporting slower.

account_balance

4 · Simplicity vs Administrative Precision

Decision: Hide ward / corporation / department complexity.

Why: The system should translate citizen input into administrative routing.

Core UX Hypothesis

“If citizens can report an issue using only location, issue type and optional evidence, while receiving clear post-submission status updates, they will be able to complete civic reports with less cognitive effort and greater confidence.”

Presentation Q&A

When they ask: “Tell us about your solution.”

“I approached the problem by looking at where civic apps currently place complexity. A citizen knows what they saw and where they saw it, but they shouldn't have to understand wards, corporations or departments to report it. So I designed the experience around a simple principle: ask the citizen only what they know and let the system handle the administrative complexity. I also introduced verification and privacy considerations so that transparency doesn't come at the cost of citizen safety.”

“Why didn't you show recent reports?”

“I initially considered showing recent reports in the user's area. But I identified two risks. First, a nearby report could potentially expose the reporter in a small community. Second, a submitted report isn't necessarily a verified issue. So I changed the public-facing section to Community Progress, which focuses on verified or processed civic outcomes rather than exposing raw citizen submissions.”

“Why is verification a separate status?”

“Because submission and truth are two different states. A report can be duplicated, incorrectly located, outdated or potentially invalid. I didn't want the UI to imply that every citizen submission is automatically confirmed. So I introduced a lightweight verification stage between receiving and assigning the report.”

“Why is the description optional?”

“Because the goal is frictionless reporting. Location, issue category and a photo can provide substantial initial context. Making a detailed written description mandatory would increase cognitive load and potentially cause abandonment.”

“Why not show the department?”

“Because that's system complexity rather than user value. The citizen knows there is a pothole; they don't necessarily know which department or corporation owns that responsibility. I would let the backend route the report automatically.”

“What would you build next?”

“My next priority would be duplicate detection and resolution verification. If multiple citizens report the same issue, the system could consolidate those reports instead of creating duplicate work. And when an issue is marked resolved, I would provide before-and-after evidence and optionally ask the citizen to confirm whether the problem was actually fixed.”

“Where could AI help?”

“AI could support the workflow rather than define it. For example, it could classify an uploaded image as a pothole, garbage issue or streetlight issue, detect likely duplicate reports and help route the issue to the correct department. But the citizen should always be able to correct the system's suggestion.”
